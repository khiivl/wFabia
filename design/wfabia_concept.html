Four jobs, four switches

Zlink tap

Connects to 127.0.0.1:1555 on the head unit, decodes navigation and media frames with the same logic as navdecode.py, and keeps the current step, distance, lanes, road and track in one model.

Maxidot display

Turns that model plus GPS speed into two 10-cell rows (the rules from maxidot_sim.py) and sends them with the FIS link: heartbeat, registration, session byte, about 4 updates a second at most.

CAN link

Owns the CANable over USB (SLCAN, 100 kbit/s, termination off). Everything that touches the bus goes through it, so the display, the sniffer and later automations never fight over the adapter.

adb CAN bridge

A local socket you reach with adb forward. Stream every frame to the PC, filter them, and send frames, with the CANable staying in the car.

How the pieces connect

Because the CANable sits on the comfort bus, it sees the whole bus in the car (ignition state, door and lock status, whatever the other modules say), not only the cluster. That is what makes the sniffer and later automations possible.

The CAN broker is the heart of it

The Maxidot link has strict timing (about 250 ms per message, acks on every fourth packet, heartbeat every 230 ms). A sniffer or a sender that talks to the adapter on its own would break that. So the adapter has exactly one owner.

Receive

One reader thread parses SLCAN lines and hands each frame to all subscribers. The FIS link only wants 0x2E8, 0x699 and 0x40C. The bridge gets whatever filter the PC asked for. A ring buffer keeps the last few thousand frames for late joiners.

Transmit

One writer thread, three priorities: heartbeat first, FIS packets second, everything else third. User frames go out between FIS messages, never inside one. If the queue grows, user frames are dropped and the drop is reported, never the heartbeat.

Failure

Adapter unplugged or bus-off: the display stops, the module shows "no link", and the service re-opens the adapter every 3 s and re-registers with the cluster (new session byte) on its own.

CAN over adb, with the CANable in the car

Yes, this works. The adapter stays plugged into the head unit and the PC only needs adb, over USB or wirelessly (adb tcpip 5555), so you can work on the car from the garage or the driveway.

# on the PC
adb forward tcp:7788 tcp:7788
python wfabia.py candump --filter 0x2E8,0x699     # live frames, candump style
python wfabia.py cansend 0x4D9#08C0B9             # refused unless Send is switched on in the app
python wfabia.py zlink                            # raw Zlink frames; navlive.py attaches here
python wfabia.py log drive.jsonl                  # CAN + Zlink in one timestamped file

The wire format is one JSON object per line over the socket, so the PC tool is about 100 lines and anything else can talk to it:

→ {"op":"sub","ch":["can","zlink"],"can_ids":["0x2E8","0x699"]}
← {"ch":"can","t":1761731034.512,"dir":"rx","id":"0x40C","d":"19000000"}
← {"ch":"zlink","t":1761731034.600,"type":"0x8006","raw":"0a1f…"}
→ {"op":"tx","id":"0x5A0","d":"01FF","ttl_ms":500}
← {"ch":"ctl","ev":"tx_refused","why":"send_disabled"}
→ {"op":"module","name":"fis","enabled":false}

The one-client limit on port 1555 stops being a problem here: wFabia is the only client and relays the raw frames to the PC, so navlive.py and recording keep working while the display runs. For single frames without the socket there is also adb shell am broadcast -a de.wfabia.CAN_TX --es id 0x5A0 --es data 01FF, under the same Send switch.

Sending is off by default

Sniffing and sending are separate switches. Sending has to be armed in the app, can have an ID allowlist, and falls back to off when the service restarts.

Rules instead of code

Later features are rule files: when frames matching X arrive and condition Y holds, send Z once. "Windows up when parked" becomes a rule you can test from the PC first.

Windows up when parked: what has to be true

Nothing here is verified yet. These are the things to find out with the sniffer, in this order.

The command frame

Hold the key's lock button or the door switch while logging the bus and find what the convenience-close sends. If the comfort modules take it from a CAN frame, one frame may be enough. If the window motors are driven by hardwired lines from the door modules, CAN may not reach them at all.

Parked detection

Ignition, speed and door state should be readable from the same bus. Condition: ignition off, speed 0, all doors closed, and a one-shot trigger, never a loop.

Power and bus sleep

The head unit may power down with the ignition, and the comfort bus goes to sleep a few minutes after locking. The rule then needs the unit alive, the CANable powered, and possibly a wake frame. Check what the QF unit does at ignition off.

Safety

The door modules keep their own pinch protection, which is the reason to use the car's own close command and not to drive anything yourself. Add a confirmation or a short delay after locking so a window never moves while someone is reaching in.

Switching a module off stops its threads and releases what it held: the Zlink tap closes the socket, the display lets the heartbeat stop so the cluster blanks, the CAN link closes the USB device. Settings live in one preferences file and change at runtime, with no restart. The service starts on boot and when the CANable is plugged in, as a foreground service with a one-line notification.

Same family as wDSP and wRight

  • Shared tokens. wFabia takes the dark theme, the accent logic and the card style from wDSP's colors.xml and themes.xml. Anything that ends up in two apps (switch style, module card, section header) moves into one small shared Android library, so a change lands in all three.
  • Colour as meaning. wDSP runs red for bass to teal for treble. Here the same six colours mark the modules, from the Zlink input in red to the bridge in teal, so the order reads as the data flowing through.
  • One screen, no menus. The main screen is the module list above, sized for the head unit's touch targets. Each module expands in place for its options. A second screen only exists for the live CAN log.
  • Same code shape as wDSP. A FabiaService that owns the work, a thin activity that only shows state and flips switches. Java, Android Studio, no extra frameworks beyond usb-serial-for-android (MIT) for the CANable.

What could stop this

USB host on the K706

The CANable needs a port that acts as a USB host and gives power. Plug it in and run adb shell dumpsys usb; if it shows 16d0:117e, it works. If the ROM hides the port or grabs it, that is the first thing to fix.

Permission prompt

Android asks to allow USB access per device. With root, grant it once through an "always use this app" attach filter or install wFabia as a privileged app from the Magisk module.

Port the Python

navdecode, maxidot_sim and the FIS link are about 1,500 lines of Python. A Java port is straightforward, and the replay files we recorded become the test set: same input, same two rows.

Real radio on the bus

The Maxidot link only works with the factory radio off the bus. The head unit has to be the only "radio", which is already the plan.
